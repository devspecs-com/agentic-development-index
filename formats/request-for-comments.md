# Request for comments

## What It Is

A request for comments (RFC) is a proposal circulated for review. In software teams, the name is often borrowed from the IETF RFC series for internal changes, even though an internal RFC does not follow the IETF publication process.

## When To Use It

Use an RFC when a change crosses ownership boundaries, has meaningful alternatives, or needs broad agreement before implementation. Use a smaller decision record when the choice is already made and the main job is preserving rationale.

## Lifecycle

An RFC normally moves from draft through review to accepted, rejected, or withdrawn. Record substantive feedback and the final disposition. Accepted proposals may lead to specifications, plans, and decision records while remaining the historical proposal.

## Agent Use

Agents can summarize open questions, compare the proposal with repository evidence, and draft amendments. They should distinguish a draft proposal from an accepted instruction and should not infer acceptance from the presence of a file.

## Pitfalls

- Calling a document an RFC after implementation has already made review meaningless.
- Hiding unresolved objections in comment threads.
- Treating draft language as current policy.
- Expanding the proposal until it becomes an unreviewable program plan.

## Examples

The IETF publishes the [RFC series](https://www.rfc-editor.org/) and its standards process. Internal RFCs can borrow the review discipline while using a lighter repository-native template.
