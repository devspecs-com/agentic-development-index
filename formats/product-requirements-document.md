# Product requirements document

## What It Is

A product requirements document (PRD) describes the user or business problem a product change should solve. It usually includes goals, assumptions, scope, user flows, requirements, success measures, and open questions.

## When To Use It

Use a PRD when a team needs a shared product contract before choosing implementation details. It is most useful when several disciplines must agree on the outcome. A small fix with an obvious behavior may need only acceptance criteria.

## Lifecycle

Draft the PRD during discovery, review it with affected owners, and mark the approved scope. Keep later implementation discoveries in linked specifications or decisions. If the product direction changes, record the revision and preserve the decision trail.

## Agent Use

An agent can turn requirements into questions, acceptance checks, or bounded implementation slices. It should not invent missing product policy, convert tentative ideas into requirements, or use an old PRD without checking current status.

## Pitfalls

- Mixing product outcomes with a preselected architecture.
- Listing features without the user problem or success signal.
- Treating every brainstormed idea as committed scope.
- Letting implementation notes silently redefine the approved outcome.
